## v3：CPU / GPU 后端与场景绳梯标注

界面新增后端选择，停止后切换：`sift-cpu`（默认）、`xfeat-cpu`、`xfeat-cuda`。本机有 RTX 3080 10 GB，现有 PyTorch 2.6.0+cu124 能使用 CUDA。OpenCV 返回 CUDA 设备数 0 仅代表其构建不支持这条 GPU 路径，不能据此判断机器没有 GPU。

已接入 [XFeat 官方实现](https://github.com/verlab/accelerated_features)：神经网络地标提取、描述子匹配、候选像素校验使用 PyTorch，可选 CPU 或 CUDA；图像预处理、光流、人物和黄点仍使用 CPU。还考察了 [LightGlue](https://github.com/cvg/LightGlue) 和 [NVIDIA VPI 模板匹配](https://docs.nvidia.com/vpi/algo_template_matching.html)，本版没有集成后二者，也不把其官方单模块速度作为本程序性能。

单独使用学习特征在重复梯级和平台上出现过偏移，因此本版先提出位置候选，再用 IMG 渲染出的不透明纹理像素，在 ±24 世界像素内校验和微调；必须满足像素匹配比例和次优位置差距。前 3 个候选均拒绝时，扩大到最多 8 个。不会降低阈值来强行给坐标。当前仍是实验后端，地图素材版本、遮挡和重复结构会影响成功率。

同一批输入、每项预热一次后重复三次（2026-09-27）：

| 后端 | 全局匹配各输入的中位耗时范围 | 六个输入锁定情况 |
| --- | ---: | ---: |
| SIFT CPU | 77～121 ms | 6/6 |
| XFeat CPU | 172～231 ms | 6/6 |
| XFeat CUDA | 41～63 ms | 6/6 |

两张地图共六项输入，其中三项是已知坐标裁图，三种后端在这三项上的误差均为 0；另外三项实景截图没有独立真值，只能比较后端坐标一致性，不能宣称实景绝对误差为 0。原始记录：`output/backends_v3/report.json`。大木林Ⅱ增加了两张实景截图测试，其中一张需要扩大候选才能锁定；该补救会增加困难帧耗时。

另一个困难样本“魔法密林北郊”`101010000`（`cache/live_v3_now.png`）未能锁定：SIFT 因重复结构的次优候选过强而拒绝，XFeat 候选未通过像素校验。不能从上述六项成功样本推断所有地图都能定位；当前没有大规模标注集来统计误识别率。

完整流水线固定截图测试：大木林Ⅱ、CUDA、后台锚定、6 秒，349 帧约 **58.0 Hz**，CPU 整机口径 **10.4%**（16 逻辑核），进程 RSS **1440 MB**；镜头有效 341/349 帧（17 次地图锚定、324 次光流续接），初次有效约 177 ms。前台总耗时 P50 / P95 约 9.3 / 13.2 ms，绳梯标注约 0.36 / 1.05 ms。PyTorch 显存峰值分配约 113 MB、缓存保留约 198 MB，这不包含 CUDA 驱动上下文等总显存。记录：`output/performance_v3_forest_fixed_final/report.json`。

**这不是稳定 60 次/秒全局定位的证明。**固定截图测试不包含捕获和 GUI 绘制；大部分输出是有时限的光流续接，全局锚定约每 0.35 秒刷新。动态游戏还存在人物重检尖峰和重复场景失锁；测试期间游戏多次切图，旧地图会拒绝定位。`performance_v3_cuda` 使用了不匹配的地铁地图；两个 `performance_v3_forest_cuda*` 动态片段也有大量失锁，不能拿循环 Hz 当有效定位帧率。尚未完成保持同一地图的长时间动态成功率评估。

绳梯从地图 IMG 的 `ladderRope` 读取物理中轴、上下端点、ID、梯子/绳索类型及上端出口；与 Tile / Obj 渲染地标共同使用：

- 主画面标出当前可见的全部绳梯，不依赖人物是否识别成功。`L#` 表示梯子，`R#` 表示绳索。
- 橙色虚线是地图投影；绿色表示近 200 ms 内，上下两个局部纹理区域都通过了画面校验。局部搜索保留横向修正值供诊断，标线仍表示 IMG 的物理中轴。
- 端部横杠是可见线段端点，可能已被画面/UI 边界裁剪；JSON 同时保存完整世界端点和裁剪后的线段。
- 验证约每 150 ms 更新；失锁时清除标注，遮挡或验证不通过时保留橙色投影。地图总览也显示全部绳梯。
- 大木林Ⅱ实例已验证 `L#4`，世界中轴 X=-841、Y=1160～1305。示例：`output/forest_v3/last_frame.png`、`output/forest_v3_after/last_frame.png`。

## 两路坐标、人物短时预测与 v2 性能记录

视觉支路：主画面地标 → 摄像机世界坐标；原程序 `MainViewDetector.detect_player` 的名牌＋人物特征 → 脚底屏幕坐标；两者组合为视觉脚底世界坐标。只接受 `last_player_observed_time` 更新的真实识别，原接口返回的旧位置不算新测量。

黄点支路：单独创建 `MinimapTracker(enable_template_tracking=False)`，用同一原始帧检测黄点，再调用原程序 `PlatformGraph.minimap_norm_to_world`。显示原始值和 `get_snapped_player_world_pos` 的几何吸附值。没有复制正在运行的主程序内部 Kalman 状态，也不声称与其最终控制坐标逐帧完全相同。

**两路互不校正**。黄点及其世界坐标不输入视觉定位或人物预测。遮黑小地图后黄点输出失效，视觉世界坐标保持一致的集成回归测试已通过。

原程序黄点导航的参考点与脚底不同：站立吸附采用平台表面减 45。界面显示两种差值：

- 未换参考点：视觉脚底 − 黄点原始世界坐标。
- 身体参考点对照：`(视觉脚底 X, 视觉脚底 Y − 45) − 黄点原始世界坐标`。45 是默认参考约定，不是用来拟合黄点的自动校准；可在启动前修改输入框。跳跃、攀爬或不同人物标定下，它未必代表精确身体中心。

一次同帧样本：视觉脚底 `(2504, -59)`，黄点原始 `(2504, -106)`；原始差 `(0, 47)`，换参考点后差 `(0, 2)`。**坐标差不是绝对定位误差**，黄点有量化/画布偏移误差，人物脚底有标定误差，两路都不是真值。动态 8 秒样本的同帧测量对照距离中位数约 9.4 px、P95 约 13.4 px，尚未做人工真值标注。

人物漏检时，只有在此前已有足够新鲜的真实观测、建立了世界速度且摄像机仍有效时，才外推最多 **250 ms**；标记 `PREDICTED`，橙圈表示随时间增长的启发式不确定范围。这个范围不是统计置信区间。没有历史人物观测、镜头失锁或预测过期时输出无效。仅凭镜头移动无法确定人物是否被击退、转向、跳跃或停止。大幅人物跳变需要连续两次一致观测再接纳。

性能优化：全局 SIFT 匹配改为后台线程；前台最多跟踪 160 个空间分散地标，使用半尺寸 LK 图像。后台结果携带原始帧时间，必须先重投影到当前帧，超时、换图代际不符、光流验证失败的结果丢弃；和可靠光流矛盾的大幅世界位置修正需再次确认。界面 20 Hz，识别循环目标 60 Hz。

以下是 v2 的 **CPU SIFT** 历史记录，不代表 v3 CUDA 的内存或吞吐；v3 测试见前节。机器有 16 逻辑核：

| 测试 | 采样率 | 前台总耗时 P50 / P95 | CPU 整机口径 | 进程内存 |
| --- | ---: | ---: | ---: | ---: |
| 同一固定截图，同步全流水线，6 秒 | 32.1 Hz | 8.3 / 173.5 ms | 4.4% | 113 MB |
| 同一固定截图，后台地图匹配，6 秒 | 58.2 Hz | 7.6 / 11.4 ms | 5.9% | 116 MB |
| 动态游戏窗口，后台地图匹配，8 秒 | 43.0 Hz | 12.0 / 44.4 ms | 7.6% | 119 MB |

基准包括人物和黄点计算；固定截图不含捕获成本，两种基准均不含 GUI 绘制。带 GUI 的两个运行片段分别显示约 43.2 Hz / 9.9% CPU / 157 MB，以及 28.6 Hz / 11.3% CPU / 150 MB，人物遮挡及重检会明显影响吞吐。CPU 整机口径 = 进程 CPU 时间 / 墙钟时间 / 逻辑核数；不包括游戏和原主程序自身的资源开销。

**目前不能保证稳定 60 Hz**。v2 后台世界锚定约 160～180 ms，但不逐帧阻塞；动态场景主要剩余尖峰是人物遮挡/丢失后的全屏重新识别。要进一步稳定 60 Hz，可将人物重检也异步化并按观测时间融合、减少重检范围；不能把插值输出或只计光流的速度当成 60 次真实识别。

结果文件：`output/performance_v2/report.json`（动态）、`output/performance_v2_fixed/report.json`（固定输入）。

## 抓绳梯和脱困的适用范围

可以用视觉世界坐标筛选目标绳梯、判断目前平台、发现主坐标停滞/跳变，并为重规划提供新的位置依据。v2 已显示附近 WZ 绳梯的投影中轴及横向距离。

v3 已增加全部绳梯投影和局部画面核验，但 `control_ready` 仍为 false。精准抓梯还需确认人物脚底新鲜且不在预测态，再由原控制器验证抓稳。脱困还需结合当前目标、按键、位移和动作超时来区分“位置识别错”与“路线/动作失败”；单靠无位移不能判定卡死。此实验没有接入自动抓梯和自动脱困控制，也没有测其成功率。

## 使用

- 上方是主画面，绿色点是匹配地标；下方由原始 Tile / Obj 拼合整张场景，黄色矩形表示摄像机视野，红点表示角色。
- `已锁定`：当前帧已由地图地标确认；`短时光流推算`：沿用最近的地图锚点，最多 0.8 秒；`定位丢失` / `位置不唯一`：不输出坐标。
- `视野左上角世界坐标`是摄像机的位置，不能当作角色位置。角色世界坐标 = 摄像机坐标 + 角色画面坐标 / 画面倍率。
- 默认加载原程序的名字牌、左右特征、服饰和两段式标定文件，使用原程序脚底输出。点击**标定角色**可另外框选名字牌并点脚底；实验标定只在与原程序本帧人物位置相近时作为脚底校准使用，不单独建立人物身份。文件只保存在本实验目录。
- `画面倍率`是屏幕像素 / WZ 世界像素，普通客户端通常为 `1.0`。如果游戏本身放大到 150%，填写 `1.5`；它不是 Windows 设置中的 DPI 数字。
- `重新定位`会丢弃光流历史；`保存诊断`保存原始画面、匹配可视化、世界视野和坐标 JSON。

## 定位方法

1. 从 `Map/Map/MapN/<ID>.img` 读取各层的 Tile / Obj 实例和世界坐标。
2. 从 `Map/Tile` 和 `Map/Obj` 解码平台、房屋、绳梯等素材，处理原点、翻转、层次和 UOL 链接，渲染静态场景。背景滚动层、NPC、怪物、动画的非首帧不参与地图渲染。
3. 从渲染场景提取 SIFT 地标。画面预先屏蔽左上角 30% 宽 × 38% 高、顶端 8% 和底部 14%，这些像素既不参与全局匹配也不参与光流。
4. 保留每个画面特征的多个地图候选，用平移投票形成位置假设，再以不同地标数量、空间分布、残差和次优候选做验证。至少 12 个分散地标，次优候选少于第一名的 80%，才输出全局位置。
5. 两次地图匹配之间，只跟踪已确认地图地标的 LK 光流，并做前后向一致性检查。地图锚点每约 0.35 秒发起后台刷新，镜头失效后最多续接 0.8 秒；人物预测独立限制在 0.25 秒。

这借鉴 SLAM 的地标定位和视觉里程计；因为地图已经存在，它是**已知地图上的视觉重定位**，不是激光测距或完整的建图 SLAM。这里只求 2D 平移，画面倍率由使用者提供，不估计旋转。

地图缓存位于 `cache/`，会检查源文件尺寸和修改时间。`wz_adapter.py` 仅在本实验进程内修正随项目附带的解析器对经典 `Convex2D` 点列表的读取方式，没有修改共享解析器文件。地图链接 `info/link` 暂要求手动填写目标 ID；其他不支持的素材会写入缓存元数据的 `warnings`，界面加载时也会显示数量。

- 11 项回归测试通过：已知坐标裁图、随机覆盖小地图区域、大面积遮挡、镜头滚动方向、1.5 倍缩放、黑屏失锁、光流超时、错误地图拒绝、重复场景歧义、重复名字牌拒绝和 WZ 解码完整性。已知位置裁图误差门槛为 1～1.5 世界像素。

## 当前限制

大片重复地砖可能没有唯一解；素材版本不一致、动画遮挡和纯背景区域也可能丢失定位。窗口捕获沿用项目的 PrintWindow / BitBlt，只做读取；旧客户端在遮挡或最小化时可能无法提供有效画面，实时界面在最小化时暂停。保持游戏可见能减少捕获问题。

默认小地图屏蔽范围适用于当前左上角布局。若移动或扩大了小地图，应调整 `localizer.py` 中 `scene_mask` 的遮罩后再做“无小地图”实验。地图名选择、倍率、角色标定暂为人工配置；该程序尚未接入导航或自动操作。

运行依赖沿用当前项目的 Python 环境：OpenCV（含 SIFT）、NumPy、Pillow、psutil，以及随项目附带的 `wz_python_tool` 解析器及其依赖。桌面界面使用 Python 自带 Tkinter。
